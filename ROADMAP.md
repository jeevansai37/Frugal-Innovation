# Project roadmap

This roadmap records inspected code and verified checks. It does not imply a Vercel deployment or a live Neon database review.

## Security hardening follow-up

- Added a SQLAlchemy session execution guard against bulk UPDATE/DELETE on `audit_logs`; database role privilege requirements are documented in `SECURITY_NOTES.md`.
- Added explicit Alembic revision `0004_bootstrap_claims`. A unique claim is acquired and committed with the initial Super Admin transaction to serialize concurrent bootstrap attempts on SQLite and PostgreSQL.
- Local regression tests cover audit bulk DML rejection and concurrent bootstrap through two SQLite engines. Full suite: **68 run, 66 passed, 2 PostgreSQL tests skipped** because remote database access was prohibited. Test fixtures used temporary SQLite databases; no existing database was migrated and no remote database was contacted.

## Complaint activity history (implemented on current development branch)

- Added explicit forward-only Alembic revision `0003_complaint_history`, an indexed append-only application event table referencing existing complaint IDs. It does not alter complaint rows or backfill legacy events.
- Intake, staff status transitions, remarks, and resolution write corresponding history in the same transaction as the related complaint insert/update. Staff update form keys prevent duplicate events when a request is replayed.
- Student and authorized department-scoped staff detail pages show the chronological timeline. Invalid student tracking credentials and out-of-scope staff cannot access history. Legacy remarks remain visible with unknown original time.
- Verification: migration tests **8 passed**, complaint web-flow tests **33 passed**, identity/authorization tests **12 passed**; full suite **66 run, 64 passed, 2 optional PostgreSQL tests skipped**. The suite ran with `POSTGRES_TEST_DATABASE_URL` unset. `git diff --check` is recorded in `COMPLAINT_HISTORY_REPORT.md`.
- Migration was tested only against synthetic temporary SQLite databases. No existing local database, Neon database, or Production resource was modified. PostgreSQL execution is unverified until `POSTGRES_TEST_DATABASE_URL` is configured to a disposable test database.

## Verified implementation

- **Complaint intake and confirmation:** `/` provides Submit, Track, and Staff Login actions. `/complaint` accepts name, roll number, location, category, and description; validates values; assigns priority; and generates complaint IDs and one-time eight-digit access codes. The success page offers a private tracking link whose credentials are in the URL fragment; the fragment is converted to a CSRF-protected POST by the tracking page.
- **SQLite and PostgreSQL:** local development still defaults to `complaints.db`; `DATABASE_URL` selects PostgreSQL. PostgreSQL uses a lazy psycopg connection pool with configurable per-instance cap `DB_POOL_MAX_SIZE` (default 5). Schema changes use explicit Alembic migrations only; Flask import/startup performs no DDL. No SQLite complaints are copied or migrated, and `complaints.db` was not modified.
- **QR location flow:** `/qr-codes` lists six campus locations, `/qr-code/<location>.svg` generates SVG downloads, and a QR-selected location remains authoritative during complaint submission.
- **Classification and validation:** whole-word and phrase rules assign one of six categories and High, Medium, or Low priority. Names, roll numbers, locations, and descriptions have maximum lengths of 100, 50, 150, and 2,000 characters; supported status changes are validated.
- **Student tracking privacy:** `/student` requires complaint ID and access code via POST. New codes require exactly eight ASCII digits; legacy SHA-256 access hashes remain verifiable and unchanged. Invalid credentials return a generic 404. Students see current status, last-update time, and the latest staff remark only after valid credentials.
- **Staff access and configuration:** `/staff/login` uses individually provisioned institutional accounts. `/dashboard`, complaint details, and `/admin` validate active identity/session version and relevant permissions. Staff-only student name and roll number are filtered by complaint department permissions. CSRF tokens remain enforced. Vercel startup still requires `DATABASE_URL` and a stable secret and enables secure session cookies. No public registration exists.
- **Dashboards:** authorized staff can search and filter complaints by status, inspect scoped details, change status through `campuscare.complaints.update_complaint_status`, and add student-visible progress/resolution remarks. The admin view remains restricted to staff with the global report permission.
- **Modern responsive UI:** intake, QR gallery, confirmation, tracking and detail, staff sign-in, maintenance dashboard and detail, admin analytics, and not-found screens share a navy, white, and teal design. Focus indication, responsive layouts, reduced-motion handling, status badges, and mobile table overflow are included. `public/static/style.css` mirrors `static/style.css` for the Vercel CDN.
- **Vercel preparation:** `app.py` is the Flask entry point, `.python-version` pins Python 3.13, and `vercel.json` includes templates and static files in the function bundle. QR links prefer explicit `APP_BASE_URL`, otherwise use Vercel's per-deployment `VERCEL_URL`, then local `http://localhost:5000`. README documents an isolated empty Neon Preview database, pooled URL, Vercel variables, and smoke flow. No preview or production deployment was created.
- **Automated checks:** latest full run: 58 tests, 56 passed, and two optional PostgreSQL tests skipped because `POSTGRES_TEST_DATABASE_URL` is not configured. The synthetic end-to-end route test covers home, submission, private tracking link, individual staff login, status/remark updates, and student verification through resolution. Migration tests preserve synthetic legacy IDs/statuses/hashes and verify the two nullable Stage 2 columns. PostgreSQL dialect DDL compiles, but PostgreSQL migrations were not executed.
