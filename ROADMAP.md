# Project roadmap

This roadmap records inspected code and verified checks. It does not imply a Vercel deployment or a live Neon database review.

## Verified implementation

- **Complaint intake and confirmation:** `/` and `/complaint` accept name, roll number, location, and description; validate required fields and size limits; classify and prioritize reports; and generate complaint IDs and one-time eight-digit access codes. Codes are stored as salted scrypt hashes, and the confirmation response is not cached.
- **SQLite and Neon PostgreSQL:** local development still defaults to the existing `complaints.db`; `DATABASE_URL` selects PostgreSQL. PostgreSQL uses a lazy psycopg connection pool with configurable per-instance cap `DB_POOL_MAX_SIZE` (default 5). Schema setup creates the complaints table and adds missing columns safely. No SQLite complaints are copied or migrated. The live `complaints.db` was not modified.
- **QR location flow:** `/qr-codes` lists six campus locations, `/qr-code/<location>.svg` generates SVG downloads, and a QR-selected location remains authoritative during complaint submission.
- **Classification and validation:** whole-word and phrase rules assign one of six categories and High, Medium, or Low priority. Names, roll numbers, locations, and descriptions have maximum lengths of 100, 50, 150, and 2,000 characters; supported status changes are validated.
- **Student tracking privacy:** `/student` requires complaint ID and access code via POST. New codes require exactly eight ASCII digits; previously issued SHA-256 code hashes remain verifiable. Invalid credentials return a generic 404. Five failed attempts for a complaint and IP within 15 minutes receive a temporary 429 response. The throttle remains process-local.
- **Staff access and configuration:** staff login protects `/dashboard`, complaint details and status updates, and `/admin`. CSRF tokens are checked on POSTs. Local `.env` settings do not override process environment variables. `SECRET_KEY` is the deployment setting; `FLASK_SECRET_KEY` remains supported for local compatibility. Vercel startup requires `DATABASE_URL` and a stable secret and enables secure session cookies.
- **Dashboards:** maintenance staff can filter by priority, inspect complaints, and change status to Pending, In Progress, or Resolved. The admin view shows totals and category, location, status, monthly, and recent complaint summaries.
- **Modern responsive UI:** intake, QR gallery, confirmation, tracking and detail, staff sign-in, maintenance dashboard and detail, admin analytics, and not-found screens share a navy, white, and teal design. Focus indication, responsive layouts, reduced-motion handling, status badges, and mobile table overflow are included. `public/static/style.css` mirrors `static/style.css` for the Vercel CDN.
- **Vercel preparation:** `app.py` is the Flask entry point, `.python-version` pins Python 3.13, and `vercel.json` includes templates and static files in the function bundle. QR links prefer explicit `APP_BASE_URL`, otherwise use Vercel's per-deployment `VERCEL_URL`, then local `http://localhost:5000`. README documents an isolated empty Neon Preview database, pooled URL, Vercel variables, and smoke flow. No preview or production deployment was created.
- **Automated checks:** the SQLite/classification suite covers submission, tracking, legacy-code compatibility, throttling, validation, QR endpoints, staff authentication, CSRF, status updates, and analytics. Deployment tests cover base URL precedence and Preview QR links. An optional PostgreSQL integration test uses a uniquely named schema and synthetic records. Latest run: `\.venv\Scripts\python.exe -m unittest discover -s tests -v` ran 34 tests: 33 passed; the PostgreSQL test was skipped because `POSTGRES_TEST_DATABASE_URL` is not configured. Python compilation, Vercel JSON parsing, static asset comparison, and `git diff --check` passed. The PostgreSQL path remains unverified without a test database URL.
